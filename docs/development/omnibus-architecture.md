# Omnibus: архитектура OS-агностичного ядра и сменных OS-адаптеров

**Версия:** 1.0-draft · **Дата:** 2026-10-09 · **Статус:** архитектурное решение, companion к `omnibus-spec.md` (спека прототипа v1.0) и `omnibus-pitch.md`

Этот документ фиксирует архитектуру, вытекающую из трёх предыдущих решений: спеки прототипа (Arch-only), анализа переносимости на macOS и анализа генерализации на 4 дистро-семейства. Ключевой вывод, который архитектура обязана воплотить: **ядро контракта переносится между ОС целиком — жертвуем периферией обещаний, а не архитектурой**. Область действия — **только десктоп-реализации** целевых ОС (серверные/headless-профили вне scope v1).

Пункты, требующие фактической проверки в M0, помечены **⚠M0**.

### Карта документа (требование → раздел)

| Требование к документу | Раздел |
|---|---|
| Разделение «OS-агностичное ядро (omnibusd) ↔ сменные адаптеры» за явной границей SPI (трейты); состав ядра; реестр заменяемых подсистем; закрепление MCP-инструментов за адаптерами | §2–§5 |
| Матрица целевых платформ (7 десктопных ОС) с составом адаптеров и уровнем гарантий (tier) | §6 |
| Политика фича-детекции и деградации: `capabilities()` — единственный источник истины, version floors, tiered support, согласование с анализом переносимости | §7 (флоры и абзац согласованности — также §6) |
| Coupling-анализ границы ядро↔адаптер по Balanced Coupling Model: сила × дистанция × волатильность, connascence-аудит, демонстрация «новый OS-адаптер без изменений ядра» | §8 |

## 1. Неизменяемые принципы

| # | Принцип | Следствие для архитектуры |
|---|---------|---------------------------|
| P1 | **Contract-first, OS-second** | Инструменты MCP определяются контрактом ядра, а не возможностями конкретной ОС; ОС поставляет *реализации* за явной границей |
| P2 | **Semantics, not pixels** | Чтение — семантическое (a11y-деревья, журналы, статусы юнитов), запись — типизированная; эмуляция ввода — вне v1 (opt-in «последней инстанции» — только при доказанной потребности) |
| P3 | **Read/write асимметрия** | Чтение всегда; запись — только через типизированные методы и только по грантам, выданным человеком вне контура агента (TOML-конфиг, CLI, doctor) |
| P4 | **`capabilities()` — единственный источник истины** | Ни ядро, ни агент не «знают дистрибутив»; всё поведение выводится из машинно-читаемого отчёта о возможностях (§7) |
| P5 | **Аудит тотален** | Каждое действие агента — structured-событие; *схема* события принадлежит ядру, *приёмник* — сменный адаптер |
| P6 | **Адаптеры не сговариваются** | Адаптер никогда не вызывает другой адаптер; композиция инструментов — обязанность ядра (§8.2) |
| P7 | **Диагноз универсален, лечение дистро-осознанно** | Знания о починке — в базах знаний (дистро-доки); применимость статьи оценивает агент (у него есть `capabilities()` и контекст задачи), а не ядерная машинерия плейбуков |

## 2. Слои и карта крейтов

```
┌──────────────────────────────────────────────────────────────────┐
│  MCP-хосты: Claude Code · goose · Cursor · собственные агенты     │
└───────────────┬──────────────────────────────────────────────────┘
                │ MCP (stdio)
┌───────────────▼──────────────────────────────────────────────────┐
│  ЯДРО — omnibus-core (крейт, бинарь omnibusd) · OS-агностично     │
│   MCP-фасад (rmcp) · сессии · скоупы · аудит-пайплайн             │
│   реестр capabilities() · doctor (оркестрация трейтов)            │
└───────────────┬──────────────────────────────────────────────────┘
                │ SPI: Rust-трейты + DTO + реестр capabilities
                │ (крейт omnibus-contracts — ЕДИНСТВЕННАЯ общая зависимость)
┌───────────────▼──────────────────────────────────────────────────┐
│  АДАПТЕРЫ — крейты omnibus-adapter-* (подсистема × ОС-семейство)  │
│   a11y:        atspi (Linux)          / ax (macOS)                │
│   journaling:  journald               / unifiedlog                │
│   service:     systemd1               / launchd                   │
│   packages:    alpm / apt / dnf       / brew(+mas)                │
│   portals:     xdg-portals+wl-clip    / screencapture+notify      │
│   files:       fs-xdg                 / fs-tcc                    │
│   knowledge:   kb-archwiki · kb-guides / kb-guides (Apple, SS64)  │
│   сеть:        nm (read-only)         / — (вне v1)                │
│   probe:       детекция платформы, выбор и активация адаптеров    │
└──────────────────────────────────────────────────────────────────┘
```

**Карта крейтов и правило зависимостей (проверяемое в CI):**

- `omnibus-contracts` — трейты SPI, DTO, константы capabilities, error taxonomy, типы адресации. Зависимости: только `serde`/async-типы. **Ноль OS-зависимостей.**
- `omnibus-core` — фасад, сессии, скоупы, аудит, capabilities-реестр, doctor (оркестрирует несколько трейтов — P6). Ноль модельных вызовов: инференс целиком в контуре агента юзера.
- `omnibus-adapter-*` — по крейту на подсистему×семейство (см. §4).
- `omnibus-probe` — детекция платформы и версий, сборка отчёта capabilities, выбор адаптеров.

Направление зависимостей — ацикличное и закреплённое:

```
contracts ← adapters          contracts ← core          core ← (динамически) adapters
adapters ↮ adapters (запрещено)        adapters ↮ core::internal (запрещено, lint в CI)
```

**Решение: трейты + `dyn Trait`, а не дженерики и не плагины.** Дженерики заморозили бы набор адаптеров на этапе компиляции — это ломает runtime-детекцию платформы (P4). Динамическая загрузка `.so` отброшена: ABI в Rust нестабилен, а чистота шва обеспечивается крейтом контрактов; сторонние адаптеры = fork+build, что приемлемо для v1 и не мешает вынести контракты в отдельный репозиторий позже (§8.8).

## 3. Ядро omnibusd: что именно OS-агностично

1. **MCP-фасад** — rmcp, транспорт stdio (HTTP — вне v1); топология: omnibusd — child MCP-клиента, по инстансу на соединение (N агентов = N инстансов одного бинарника); постоянного демона и admin-канала нет — состояние = конфиг + ephemeral-сессия, координация инстансов — только file-lock (§3.9). Реестр инструментов, генерация JSON-схем из DTO.
2. **Сессии** — сессия = MCP-соединение: живёт и умирает с процессом инстанса, TTL и фоновых таймеров нет; идентификатор — только для корреляции аудита. *Все* opaque-токены (session_id, element_id) mintит только ядро.
3. **Скоупы** — TOML-манифесты (системные шаблоны `/etc/omnibus/scopes.d/*.toml` + пользовательский стор `$XDG_CONFIG_HOME/omnibus/scopes.d/90-grants.toml`, который пишет `omnibusd grant`), read-only по умолчанию. Гранты выдаёт только человек вне контура агента, ровно один механизм: записи в TOML-манифестах — руками или командой `omnibusd grant <грант>` (редактирует манифест; doctor возвращает готовую команду). «Временный» грант = выданный и отозванный: отдельного session-канала нет — при stdio-топологии конфиг статичен, различие persistent/session иллюзорно; рантайм не имеет API приёма подтверждений — ни один MCP-метод не принимает токен согласия. Принятие решений о доступе — исключительно в ядре.

   Якоря формата (имена полей фиксируются формальной спекой; состав записей — иллюстративный):

   ```toml
   # системные шаблоны — /etc/omnibus/scopes.d; `omnibusd grant <имя>` пишет пользовательский стор …/scopes.d/90-grants.toml
   [write]                                     # всё неперечисленное — deny
   "service.write"     = {}                    # → svc_start, svc_stop
   "pkg.undo"          = {}                    # → pkg_undo (скрыт без этой записи)
   "files.scope.write" = { paths = ["/home/user/Projects"] }   # параметризованный скоуп → fs_write

   [optin]                                     # capability в статусе opt-in-required
   "journal.persistent" = {}                   # согласие на мутацию; исполняет человек (doctor-CLI)
   ```

   ```json
   { "capabilities": [
     { "name": "pkg.undo",          "ver": "1.0.0", "status": "present",
       "value": "cache-downgrade",  "adapter": "alpm" },
     { "name": "journal.prev_boot", "ver": "1.0.0", "status": "opt-in-required",
       "value": false,              "adapter": "journald",
       "note": "журнал volatile; прошлые загрузки появятся после включения персистентного хранилища",
       "remedy": "omnibusd grant journal.persistent" },
     { "name": "journal.persistent","ver": "1.0.0", "status": "opt-in-required",
       "adapter": "journald",       "remedy": "omnibusd grant journal.persistent" } ] }
   ```

   (`ver` — semver контракта capability; `value` — типизированное значение для capability с вариантами; `note` — ограничения деградации; `remedy` — copy-paste-команда, тот же принцип, что у ремедиации `ScopeDenied`; отсутствие capability = отсутствие записи в документе.)

4. **Аудит** — единая схема события `{ts, session, actor, tool, adapter, op, params_hash, result, scope_ref}`; `actor` = `{uid, client_name из MCP-initialize, pid}`: транспорт stdio внутри одного uid, доверие = локальный пользователь (стандартная модель угроз desktop), отдельной аутентификации канала нет; аудит происходит на уровне фасада (адаптерам знать об этом не нужно); приёмник — трейт `AuditSink` (journald / unified log / file-fallback).
5. **`capabilities()`** — агрегатор отчётов адаптеров в один документ для агента (§7).
6. **Контракты инструментов** — каждая MCP-функция = (имя, схема, требуемые capabilities, обработчик). Инструменты с недоступными capabilities **скрываются из tool list** (§7.3).
7. **Error taxonomy** — единый словарь кодов: `CapabilityRequired`, `ScopeDenied`, `FloorUnsupported`, `AdapterUnavailable`, `NativeFailure{code}`, `ElementStale`, `TimeoutError`, `Unsupported{reason}`. Нативные коды ошибок маппятся адаптером в `NativeFailure` без потери детали (payload сохраняет исходное сообщение для диагностики).
8. **Ноль инференса** — ядро не делает модельных вызовов (ни локальных, ни облачных): triage интента, суммаризация и любая семантическая работа — контур агента юзера, где они наблюдаемы его политиками; omnibusd не создаёт теневой плоскости управления в обход политик агента и не добавляет латентности инференса.
9. **Конкурентность** — write-операции глобально сериализованы: мьютекс внутри инстанса + межпроцессный flock (`XDG_RUNTIME_DIR/omnibus/write.lock`) между инстансами; read — параллельно. Порядок применения = порядок захвата лока; аудит фиксирует фактический порядок. Ни один сценарий v1 не требует параллельных write.
10. **Лимиты и ретраи** — дефолты жёстко в коде: tool-call 10 с (`desktop.tree` — 15 с), D-Bus-операция 2 с; действующие значения видны в `capabilities()`/doctor (конфиг-поверхность переопределения — по первому реальному запросу). Ретраи: ровно один авторетрай для идемпотентных read; write не ретраются никогда; исчерпание → typed `TimeoutError` (решение о повторе — за агентом).

## 4. Граница SPI: реестр заменяемых подсистем

Явная интерфейсная граница — набор Rust-трейтов в `omnibus-contracts`. Каждая подсистема: трейт + дескриптор capabilities + правила маппинга ошибок + версия контракта (semver контракта независим от версии кода).

| # | Подсистема | Трейт | Ключевые операции контракта | Провайдер(ы) Linux | Провайдер macOS |
|---|------------|-------|------------------------------|--------------------|-----------------|
| 1 | **a11y / desktop** | `DesktopA11y` | `tree(app)`, `element(id)`, `read_attr`, `set_value`, `invoke` | `atspi` (AT-SPI2 over D-Bus) | `ax` (NSAccessibility / AXUIElement) |
| 2 | **journaling + audit sink** | `Journal`, `AuditSink` | `query(Filter{unit, boot, severity, window})`, `tail`, `write(AuditEvent)` | `journald` (персистентность зависит от дистрибутива — §6/§7) | `unifiedlog` (`log show --predicate`) |
| 3 | **service management** | `ServiceManager` | `list`, `status`, `start/stop/restart`, `enable/disable` | `systemd1` (org.freedesktop.systemd1) | `launchd` (LaunchAgent — только агенты видят GUI) |
| 4 | **package management** | `PackageManager` | `list`, `info`, `search`, `install`, `remove`, `history`, `undo` | `alpm` (Arch/Manjaro) · `apt` (Debian/Ubuntu/Mint; **undo нет**) · `dnf` (Fedora; transactional undo) | `brew` (формулы) + `mas` (App Store, опц.) |
| 5 | **portals** | `ScreenCapture`, `Notify` | `screenshot`, `clip_read/clip_write`, `notify` | `xdg-desktop-portal` + `wl-clipboard`/`xclip` | ScreenCaptureKit (+ежемесячный re-grant права в 15+) · UNUserNotificationCenter |
| 6 | **файловые скоупы** | `FileScope` | `list/read/write` в granted-скоупах, `resolve` | `fs-xdg` (XDG-каталоги) | `fs-tcc` (`~/Documents` и др.; за пределами — Full Disk Access) |
| 7 | **база знаний** | `KnowledgeBase` | `search`, `page` | `kb-archwiki` (ArchWiki + Manjaro-overlay) · `kb-guides` (дистро-доки: Debian wiki, Ubuntu docs, Mint, Fedora docs) | `kb-guides` (агрегатор гайдов: Apple Support, SS64, сообщество) |
| 8 | **платформенный probe** | `PlatformProbe` | `detect() → PlatformReport{distro/release, versions, живость демонов}` | `/etc/os-release`, `systemctl --version`, состояние шин | `sw_vers`, системные профили, TCC-гранты |
| 9 | *(опц., macOS)* **app-intents backend** | `AppIntentsBridge` | `list_actions`, `run` | — | Shortcuts / App Intents (только cooperating-приложения; **бэкенд, не замена** a11y-слоя) |
| 10 | **сеть (статус)** | `NetworkStatus` | `status()` — устройства, connectivity, wifi-сети; read-only | `nm` (org.freedesktop.NetworkManager; «когда есть» — §6) | — (вне v1) |

**Дисциплина DTO:** плоские именованные структуры (никаких кортежей), newtype-обёртки для юнитов (`Milliseconds`, `Bytes`, `Severity`), нативные типы (`zbus::Value`, хэндлы ALPM, `AXUIElementRef`) **не покидают адаптер** — маппинг в DTO выполняется внутри адаптера.

**Семантика адресации:** `tree(app)` — селектор `app` = executable basename (exact, case-insensitive) + опциональный `pid` для устранения неоднозначности; несколько совпадений → typed-ошибка со списком кандидатов (role+name+pid). Stale `element_id` (UI изменился) → typed `ElementStale`, авторазрешения нет — агент перечитывает `tree`.

## 5. Какие инструменты MCP на каких адаптерах строятся

| MCP-инструмент | Обязательные capabilities | Опирается на трейт(ы) |
|---|---|---|
| `desktop.tree` | `desktop.tree` | `DesktopA11y` |
| `desktop.element` | `desktop.tree` | `DesktopA11y` |
| `desktop.set_value` / `desktop.invoke` | `desktop.tree` + `desktop.write.typed` (+ write-скоуп) | `DesktopA11y` |
| `clip_read` | `portal.clipboard` | `ScreenCapture` |
| `clip_write` | `portal.clipboard` (+ write-скоуп) | `ScreenCapture` |
| `screenshot` | `portal.screenshot` | `ScreenCapture` |
| `notify` | `portal.notify` (+ write-скоуп) | `Notify` |
| `svc_list` / `svc_status` | `service.read` | `ServiceManager` |
| `svc_start` / `svc_stop` | `service.write` (+ write-скоуп) | `ServiceManager` |
| `journal_query` | `journal.query` (+ `journal.prev_boot` для прошлых загрузок) | `Journal` |
| `pkg_list` / `pkg_info` | `pkg.read` | `PackageManager` |
| `pkg_install` / `pkg_remove` | `pkg.write` (+ scope) | `PackageManager` |
| `pkg_undo` | `pkg.undo` (+ write-скоуп); скрыт при `pkg.undo=none` | `PackageManager` |
| `fs_list` / `fs_read` | `files.scope.read` | `FileScope` |
| `fs_write` | `files.scope.write` (+ scope) | `FileScope` |
| `wiki_search` / `wiki_page` | `kb.present` | `KnowledgeBase` |
| `net_status` | `net.read` | `NetworkStatus` |
| `intent_list` / `intent_run` *(MS3, macOS)* | `intents.list` / `intents.run` (+ write-скоуп для `run`); скрыты без actions в probe-отчёте | `AppIntentsBridge` |
| `capabilities()` / `session_info` | — (ядро) | агрегат `PlatformProbe` |
| `doctor` (ядро; оркеструет 4 трейта) | — (ядро) | `PlatformProbe` + `Journal` + `ServiceManager` + `KnowledgeBase` |

**Правило:** инструмент живёт в ядре, даже если у него единственный адаптер-бэкенд; ядро вызывает трейт, а не реализацию. Ни один инструмент не импортирует нативные крейты.

## 6. Матрица целевых платформ (desktop only)

Состав адаптеров и уровень гарантий (**tier**) по каждой платформе.

| Платформа | a11y | Журнал | Сервисы | Пакеты | Порталы / ввод | Файлы | База знаний | **Tier** |
|---|---|---|---|---|---|---|---|---|
| **Arch** | atspi | journald — persistent ✓ (подтверждено) | systemd1 | alpm (downgrade из кэша ⇒ `pkg.undo` ✓) | xdg-portal | fs-xdg | ArchWiki | **T1** |
| **Manjaro** | atspi | journald — persistent ✓ ⚠M0 | systemd1 | alpm (задержанные репы, mhwd, pamac) | xdg-portal | fs-xdg | ArchWiki + Manjaro-overlay | **T1** *(своя тест-матрица)* |
| **Debian trixie** | atspi | journald — дефолт ⚠M0; doctor включает | systemd1 257 | apt (**undo нет**) | xdg-portal; NM read-only | fs-xdg | Debian wiki | **T2** |
| **Debian bookworm** | atspi 2.46 < пола 2.50 — `desktop.*` скрыты | journald — persistent по умолчанию (M0, табл. 1) | systemd1 252 *(на полу)* | apt (**undo нет**) | xdg-portal; NM read-only | fs-xdg | Debian wiki | **T2** *(на полу; задокументированная деградация: `desktop.*` скрыты)* |
| **Debian bullseye** | atspi | journald — ⚠M0 | systemd1 247 *(ниже пола)* | apt | xdg-portal — частично | fs-xdg | Debian wiki | **T3** |
| **Ubuntu LTS** | atspi | journald — persistent по умолчанию (M0, табл. 1); факт машины, doctor включает при volatile | systemd1 255 (24.04) ⚠M0 | apt (**undo нет**); NM за netplan | xdg-portal; NM read-only | fs-xdg | Ubuntu docs | **T2** |
| **Mint** | atspi | journald — persistent (наследует дефолт Ubuntu, M0 табл. 1) | systemd1 = Ubuntu LTS | apt (**undo нет**) | xdg-portal; X11 дефолт | fs-xdg | Mint docs/forums | **T2** |
| **Fedora desktop** | atspi | journald — дефолт ⚠M0 | systemd1 (свежий) | dnf (transactional undo ⇒ `pkg.undo` ✓) | xdg-portal (свежие интерфейсы) | fs-xdg | Fedora docs | **T2** |
| **macOS desktop** | ax | unifiedlog | launchd | brew + mas | ScreenCaptureKit (+ AppIntents как опц. бэкенд) | fs-tcc | kb-guides | **T2** *(вторая цель после победы на Arch)* |

**Определения tier:**

- **T1 — «гарантированный контракт»:** полный набор инструментов, read+write, диагностика прошлых загрузок из коробки, `pkg.undo` по возможностям пакетного менеджера, CI на каждый релиз ядра и адаптеров, документированных деградаций нет.
- **T2 — «полное чтение + безопасная запись»:** всё чтение гарантировано; write — там, где capability объявлена; задокументированные деградации: у apt нет транзакционного undo (инструмент честно не обещает откат), `journal.prev_boot` — при факте прошлых загрузок (машины, пробеченные volatile: opt-in персистентности через doctor, затем перезагрузка), сеть — read-only; на нижней границе полов (bookworm) at-spi2 ниже пола скрывает `desktop.*` — задокументированная деградация строки, не отдельный тир. CI — smoke на эталонных версиях.
- **T3 — «community»:** сборка существует, `capabilities()` отчитывается честно; часть интерфейсов ниже version floor отсутствует; гарантий нет, поддержка сообществом.

Платформенные особенности — примечания матрицы, а не отдельные категории: Manjaro — контракт T1 со своей тестовой матрицей и оговорками по свежести пакетов (mhwd, pamac, задержанные репы); Debian bookworm — T2 на нижней границе полов (systemd 252 — на полу; at-spi2 2.46 ниже пола 2.50 — `desktop.*` скрыты, FloorUnsupported; остальные подсистемы активны, smoke на эталоне); Fedora — T2 плюс transactional undo (dnf) и самые свежие portal-интерфейсы. Машинная правда особенностей — `capabilities()`.

**Version floors (версионные полы):**

- systemd **≥ 252** — пол для T2 (bookworm = 252 на полу; bullseye = 247 ниже пола → T3).
- AT-SPI2 — пол фиксируется по итогам M0-замеров ⚠M0.
- macOS **≥ 14** (обоснование: ServiceManagement 13+ и запас; рекомендуемый 15+ ⚠M0 — учтён ежемесячный re-grant Screen Recording в doctor).
- Wayland — portal-интерфейсы по версии `xdg-desktop-portal`; X11-пути — без пола.
- varlink — вне гарантий T2 (только при свежих systemd); основной путь — D-Bus.

**Согласованность с предыдущим анализом переносимости:** persistent journald по умолчанию есть во всех шести семьях на свежих установках (M0, табл. 1); волатильность — конфигурация конкретной машины, включается через doctor; транзакционного undo у apt нет — `pkg.undo` объявляют только alpm (downgrade из кэша) и dnf (transactional undo); NetworkManager не универсален (Ubuntu Server — netplan+networkd, Debian — трёхвариантный выбор) ⇒ сетевые write-действия вне v1, NM read-only «когда есть»; macOS: AX API зрелее AT-SPI2, но гейт — TCC-права (Accessibility, Screen Recording с ежемесячным re-grant, Automation, Full Disk Access), программная выдача — только MDM/PPPC.

## 7. Политика фича-детекции и деградации

### 7.1. `capabilities()` — единственный источник истины

- Формат capability: `{domain}.{feature}[.{qualifier}]` + версия (semver) + статус (`present` / `degraded` / `opt-in-required`); для capability с вариантами исполнения — типизированное значение-enum из contracts. Примеры: `desktop.tree`, `desktop.write.typed`, `journal.persistent`, `journal.prev_boot`, `service.write`, `pkg.undo` (значение-enum: `none`/`cache-downgrade`/`transactional`), `portal.screenshot`, `files.scope.tcc`. Пример собранного документа — §3.3.
- Реестр имён — константы в `omnibus-contracts` (один источник; литералы в коде запрещены).
- Адаптер при старте отчитывается через `PlatformProbe` → реестр → `capabilities()` собирает документ: что доступно, на каком адаптере, с какой версией, с какими ограничениями. Агент **не должен ничего предполагать**: отсутствие capability выражается отсутствием инструмента, а не runtime-ошибкой.

### 7.2. Три уровня детекции

1. **compile-time** — feature-флаги крейтов адаптеров (сборка под семейство ОС);
2. **install-time** — выбор пакета (PKGBUILD ставит linux-набор, Homebrew formula — macos-набор);
3. **runtime** — probe проверяет версии и живость демонов (systemd1 на шине, AT-SPI в сессии, TCC-гранты) → финальный отчёт capabilities. Runtime-отчёт перекрывает первые два.

Изменения (doctor-CLI, правки конфига) подхватываются новой сессией: инстанс = child MCP-клиента, каждая новая сессия делает свежий probe и получает актуальный tool list; отдельный inotify/файл-флаг и уведомления живому инстансу не нужны — машинерия мониторинга не окупает экономии одного переподключения.

### 7.3. Поведение при деградации (по возрастанию тяжести)

1. **Деградированная capability** — инструмент присутствует, схема помечает ограничения (пример: `pkg_install` без `pkg.undo` на apt);
2. **Отсутствующая capability** — инструмент скрыт из tool list; прямой вызов по имени → ошибка `CapabilityRequired` с подсказкой doctor;
3. **Ниже version floor** — адаптер вообще не активируется; `capabilities()` объясняет причину (пример: «systemd 247 < 252»);
4. **Грант не выдан** (TCC) — capability в статусе `opt-in-required`; doctor ведёт через выдачу; до гранта поведение = (2).

### 7.4. Политика включений (что ядро может менять в системе)

- **Никогда через агента:** любые write-действия — только по грантам, выданным человеком вне контура агента (TOML, `omnibusd grant`, doctor); рантайм не имеет API приёма подтверждений — in-band «пользователь подтвердил» от агента неотличим от подделки. Отказ → `ScopeDenied` с copy-paste-ремедиацией в одну команду.
- **Opt-in через doctor, с явным согласием:** включение персистентного journald (`mkdir /var/log/journal` + restart, исполняет человек; грант `omnibusd grant journal.persistent` — только политика) — открывает флагманскую диагностику прошлых загрузок на любой машине с volatile-конфигом journald; включение a11y-флагов у Electron-приложений. Канал тот же, что у грантов: мутации исполняет только человек — CLI-режим `omnibusd doctor` (или выполнение выданной им команды); doctor, вызванный агентом через MCP, только диагностирует и возвращает copy-paste-ремедиацию — мутировать систему он не может ни при каком ответе агента.
- **Никогда:** смена сетевого бэкенда, бэкпорты systemd, изменение системных политик безопасности (TCC выдаётся только человеком через GUI или MDM/PPPC).
- **Принятый риск (read):** `screenshot` на Linux — без нашего гейта: Wayland защищает портал DE (не контракт Omnibus), X11-путь системного гейта не имеет; пересмотр — opt-in-грант по доказанному спросу. На macOS гейт — TCC.

### 7.5. Соотношение tier и capabilities

Tier — категория *обещаний и тестирования* (что мы гарантируем и что прогоняем в CI); `capabilities()` — *машинная правда* конкретной машины. Расхождения возможны и ожидаемы (пример: Fedora с volatile-журналом покажет `journal.prev_boot=false` раньше, чем мы пересмотрим tier) — источник истины в спорных случаях всегда capabilities().

## 8. Анализ связанности границы ядро↔адаптеры (Balanced Coupling Model)

Оценка по методике: **интеграционная сила × дистанция × волатильность**, затем connascence-аудит границы и демонстрация ключевого свойства — *добавление нового OS-адаптера не требует изменений ядра*.

### 8.1. Карта компонентов

- **Ядро** (`omnibus-core`): фасад, сессии, скоупы, аудит, capabilities-реестр, doctor (оркестрация трейтов).
- **Контракты** (`omnibus-contracts`): 12 трейтов SPI (10 подсистем), DTO, реестр capabilities, error taxonomy, типы адресации.
- **Адаптеры**: ~15 крейтов (подсистема×семейство) + probe.
- **Характер связей:** ядро → адаптеры — через `dyn Trait` (реестр, собранный probe'ом); адаптеры → контракты; адаптер↔адаптер — запрещено (P6).

### 8.2. Сила интеграции на границе

| Связь | Тип силы | Обоснование |
|---|---|---|
| ядро → контракты | **Contract** | Только явные интерфейсы: трейты, DTO, константы capabilities |
| адаптер → контракты | **Contract** | Адаптер видит только сигнатуры трейтов и DTO; нативные типы не покидают адаптер |
| ядро → адаптер | **Contract** | Вызов через trait object; интрузивная связь невозможна по построению (запрет `omnibus_core::internal` в адаптерах — lint в CI) |
| адаптер → адаптер | **отсутствует** | by design (P6); оркестрацию трейтов (doctor) ведёт ядро |
| внутри ядра | Functional/Model | Общая модель сессий и скоупов — нормально: это одна территория |
| внутри адаптера | Intrusive (к нативным API) | Это и есть его работа: маппинг к конкретной ОС |

Итог: максимальная сила интеграции **через границу** — Contract (слабейший из четырёх уровней). Логика remediation не дублируется и не разделяется через границу: знания «как чинить» — в KB-провайдере (P7), политика доступа — в ядре, в адаптерах — только маппинг к нативным API.

### 8.3. Дистанция

- Контракты и адаптеры — разные крейты/неймспейсы (дистанция 3–4 по шкале «методы → классы в файле → неймспейс → крейты → репозитории → команды»); при росте проекта вынос контрактов в отдельный репозиторий повышает дистанцию **без изменения контрактов**.
- Внутри ядра — один крейт (малая дистанция).

### 8.4. Волатильность (классификация поддоменов)

- **Контракты инструментов и реестр capabilities** — Core-поддомен продукта (агентный контракт — конкурентное преимущество, будет эволюционировать). Но это *тектоническая плита ядра*: ядро и контракты релизятся вместе, дистанция внутри плиты нулевая — сильная/средняя связь при малой дистанции допустима.
- **Реализации адаптеров** — волатильность высокая по краям (dnf→dnf5, версии порталов, TCC-политики macOS) и низкая по контракту. Граница запирает высокую волатильность в крейтах-адаптерах, удалённых друг от друга (матрица Manjaro ≠ Debian ≠ macOS) и от ядра.
- **MCP-протокол** — generic-поддомен, стабилен; изолирован в ядре (rmcp за обёрткой фасада).

**Матрица баланса:**

| Пара | Сила | Дистанция | Волатильность | Баланс |
|---|---|---|---|---|
| ядро → адаптер (через SPI) | Contract (слабая) | высокая | высокая (реализации) | ✅ слабая×далёкая |
| адаптер → адаптер | нет связи | высокая | высокая | ✅ связанности нет |
| внутри ядра | Functional/Model (сильная) | минимальная | низкая-средняя | ✅ сильная×близкая |
| внутри адаптера | Intrusive (сильная) | минимальная | высокая | ✅ сильная×близкая |
| ядро ↔ contracts | Contract (слабая) | минимальная (один воркспейс) | поверхность стабильнее реализаций; semver | ✅* слабая×близкая — осознанный компромисс |

**Проверка формулы модулярности** `MODULARITY = (STRENGTH XOR DISTANCE) OR NOT VOLATILITY`:

- ядро↔адаптер: слабая сила XOR высокая дистанция = ✅ (высокая волатильность реализаций не вредит — сила слабая);
- внутри ядра и внутри адаптера: сильная сила при малой дистанции = ✅;
- ядро↔contracts: слабая×близкая — формально «лишняя абстракция», но оправдана ролью сборочной точки для адаптеров и низкой волатильностью самой поверхности контрактов (исключение по волатильности), плюс это единственный шов, делающий возможной первую строку таблицы;
- **нарушений типа «сильная связь × большая дистанция» (распределённый монолит) нет** — это главный проверяемый вывод.

Косвенные метрики (CBO > 14, индекс нестабильности 0.3–0.7 для часто меняющегося кода) применимы после появления кода; на этапе дизайна их аналоги — правила зависимостей крейтов (§2) и гейты CI. Целевая форма по Stable Abstractions Principle: `omnibus-contracts` — максимально стабильный и максимально абстрактный (I→0, все зависят от него, он ни от кого), адаптеры — конкретные и нестабильные (I→1).

### 8.5. Connascence-аудит границы

**Статические:**

- **CoN (имена)** — присутствует по необходимости (имена capabilities, инструментов, методов трейтов); ослаблен тем, что имена объявлены однократно в `omnibus-contracts` как экспортируемые константы — дублей литералов нет.
- **CoT (типы)** — DTO на границе; это и есть контракт. Дисциплина: плоские именованные структуры, semver контрактов, нативные типы не проходят.
- **CoM (смысл значений)** — риск юнитов и конвенций (мс/сек, байты/КиБ, уровни severity). **Преобразовано в CoT** newtype-обёртками (`Milliseconds`, `Bytes`, `enum Severity`).
- **CoP (позиция)** — **исключено стилем**: все сигнатуры трейтов принимают именованные структуры (никаких tuple-параметров).
- **CoA (алгоритм)** — через границу не идёт: единственное разделяемое — сериализация DTO (часть контракта); алгоритмы обхода a11y-дерева, разрешения адресов элементов, дельта-чтения журнала — собственность адаптера, контракт задаёт только вход/выход (адресация opaque-токенами).

**Динамические:**

- **CoE (порядок выполнения)** — жизненный цикл адаптера `probe → register → serve → shutdown` — конечный автомат, принадлежащий ядру; адаптер физически не может быть вызван до register. Порядок вызовов инструментов внутри сессии свободен.
- **CoTm (тайминг)** — таймауты и ретраи — параметры политики ядра, передаваемые в контракте; собственных тайм-допущений у адаптеров нет.
- **CoV (согласованные значения)** — пара «версия контракта ↔ версия capability» сходится в едином реестре; capability не может объявиться вне контракта.
- **CoI (идентичность)** — все handle (session_id, element_id) mintит ядро; адаптеры получают opaque-токены и не зависят от инстансов внутренних объектов ядра (и наоборот).

**Проверка правил коннасценции:** (1) общая коннасценция минимизирована — через границу проходят только CoN+CoT, слабейшие статические формы; (2) коннасценция через границу минимизирована — сильнейшие формы (CoA/CoE/CoI) заперты внутри компонентов; (3) внутри компонентов допускается любая; (4) сильные преобразованы в слабые: CoM→CoT (newtypes), CoP — исключён (named structs), CoE→явный автомат ядра, CoI→opaque-токены, CoA→единственное определение в contracts; (5) с ростом дистанции коннасценция слабеет — на самой дальней границе системы осталась только слабая статическая (CoN+CoT). Статическая всегда обнаруживаемее динамической — граница проверяема компилятором и линтами, а не рантаймом.

### 8.6. Демонстрация: добавление нового OS-адаптера без изменений ядра

Сценарий: добавляем поддержку NixOS (systemd-семейство, свой пакетный менеджер) и гипотетически Windows.

1. Новый крейт `omnibus-adapter-nix`: реализует `PackageManager` (nix generations как `history`/`undo`), переиспользует готовые `atspi`/`journald`/`systemd1`.
2. `omnibus-probe`: ветка детекции `/etc/os-release` → выбор адаптера.
3. capabilities: если новая реализация не вводит новых фич — `capabilities()` меняет только провайдера; если вводит — добавляется capability-константа в contracts (**аддитивно**, минорная версия контракта).
4. **Ядро: ноль изменений.** Реестр принимает любого реализатора трейтов; инструменты ссылаются на capabilities, а не на адаптеры (§5).

**Что механически запрещает регресс:** contract test suite в `omnibus-contracts` — обязательный поведенческий набор для каждого трейта; CI гоняет его против каждой реализации. «Добавил адаптер — ядро не тронул» проверяется и негативно: PR, в котором адаптер зависит от `omnibus_core`, не собирается (запрет зависимостей).

**Обратный сценарий** (замена провайдера без изменения контракта): dnf → dnf5 — целиком внутри `omnibus-adapter-dnf`; сигнатуры и capabilities не меняются.

**Единственный случай, требующий касания ядра:** новый *тип* подсистемы (новый трейт) — и это аддитивное расширение (новый реестр), не ломающее изменений. В v1 таких два, оба just-in-time: сеть (`NetworkStatus`, Ф2.2.3) и AppIntents (`AppIntentsBridge`, Ф3.6.2) — трейт объявляется в `omnibus-contracts` вместе со своей первой реализацией, а не заранее; далее реестр §4 закрыт по списку задач спеки.

### 8.7. Красные флаги, которых архитектура сознательно избегает

- Интрузивная связь: адаптеры не дотягиваются до внутренних структур ядра (lint + ревью).
- Дублирование бизнес-логики: remediation — в KB, политика скоупов — в ядре; в адаптерах — только маппинг к нативным API.
- Требование синхронных релизов ядра и адаптеров: контракты версонируются отдельно; breaking-изменения — только мажорной версией (окно совместимости появится вместе с первым внешним потребителем контрактов).
- Циклы зависимостей: невозможны направлением (contracts ← всё; adapters ↮ adapters).

### 8.8. Рекомендации по закреплению (по убыванию приоритета)

1. **Contract test suite как gate для всех адаптеров** — это и есть механическая гарантия «новый адаптер не требует изменений ядра».
2. Закодировать правила коннасценции в clippy-линтах: запрет tuple-сигнатур в трейтах (CoP), запрет нативных типов в contracts (утечка CoT в Intrusive), запрет литералов имён capabilities (CoN).
3. Вынести `omnibus-contracts` в отдельный репозиторий при первом внешнем контрибьюторе адаптера (повышение дистанции без смены контрактов).
4. Не вводить адаптер↔адаптер вызовы даже «для удобства» — только оркестрация в ядре (как doctor).

## 9. Эволюция и совместимость

- Контракты: semver; минорные версии — аддитивные capabilities; breaking-изменения — только мажорной версией, с миграцией (окно совместимости появится вместе с первым внешним потребителем контрактов).
- На каждую подсистему **активен один адаптер** (выбирает probe); несколько реализаций допускаются только как fallback — это упрощает модель поведения и аудит.
- Удаление capability — только мажорной версией; deprecation-механика (`deprecated` → скрыта из дефолтного `capabilities()`) — по первому релизу, которому она реально понадобится.

## 10. Открытые вопросы (⚠M0)

- Дефолт персистентности journald на Debian (trixie/bookworm/bullseye), Fedora, Manjaro — влияет на подсказки doctor, не на архитектуру.
- Фактический пол AT-SPI2 по матрице DE (GNOME/KDE/XFCE/Cinnamon/MATE).
- Качество Rust-байндингов к AX (objc2) — влияет на оценку трудоёмкости macOS-адаптера, не на контракт.
- Поведение TCC в headless/SSH-сессиях — влияет на CI-стратегию macOS, не на контракт.
- systemd-версия в актуальном Ubuntu LTS — подтвердить 255 для таблицы полов.
